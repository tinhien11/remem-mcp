I tested it on honojs/hono — a TypeScript web framework with 326 source files, 4,769 tests. The task: fix issue #4992, a real open bug about Set-Cookie headers being lost when middleware and handlers both set cookies.

The bug: Set-Cookie headers lost

When a middleware sets a Set-Cookie header via c.header() before await next(), and the downstream handler returns a raw Response with its own Set-Cookie headers, one side's cookies are always lost.

The issue identifies two scenarios:

Scenario Condition Result
A No middleware touches c.res early Middleware cookies lost — #preparedHeaders never merged
B Some middleware accesses c.res early (e.g. CORS) Handler cookies lost — delete('set-cookie') wipes them

Reproducing the bug — real test failures

I wrote a test that reproduces both scenarios from the issue:

// Scenario A: no early c.res access
app.use(async (c, next) => {
  c.header('Set-Cookie', 'mw_cookie=hello; Path=/', { append: true })
  await next()
})
app.get('/test', (c) => {
  const res = new Response('ok')
  res.headers.append('set-cookie', 'handler_cookie=world; Path=/; HttpOnly')
  return res
})

// Scenario B: early c.res access (triggers #res creation)
app.use(async (c, next) => {
  c.res.headers.set('X-Something', 'true')
  c.header('Set-Cookie', 'mw_cookie=hello; Path=/', { append: true })
  await next()
})

Both tests failed against the unmodified codebase:

× should preserve both middleware and handler Set-Cookie

Bug confirmed. Both scenarios lose cookies as described in the issue.

Fix attempt 1 — 15 regressions

My first fix changed the guard from if (this.#res && _res) to if (_res), and merged headers from both #res and #preparedHeaders. The set-cookie merge logic collected cookies from both context and handler before mutating.

The 2 new tests passed. But the full suite revealed 15 regressions across 5 files:

Test Files  5 failed | 142 passed (147)
     Tests  15 failed | 4755 passed (4805)

Failures in compose, hono, cache, compress, logger — all related to response headers being merged differently than expected.

Fix attempt 2 — still 14 regressions

I realized the set-cookie handling was inside a for...of loop over Headers.entries(), which yields each set-cookie header separately — so the merge code ran once per cookie, causing duplicates. I moved set-cookie handling outside the loop.

Result: 15 → 14 failures. One fewer, but still broken. The remaining failures were because I was merging #preparedHeaders even when #res already existed — causing stale duplicate headers.

Fix attempt 3 — scoped to Scenario B

I discovered the root cause of the regressions: Scenario A and existing tests are in direct conflict. Existing tests expect #preparedHeaders NOT to be merged into raw Response objects. But issue #4992 Scenario A wants them merged. Both can't be true.

I scoped the fix to Scenario B only — keeping the original guard if (this.#res && _res), but fixing the set-cookie merge to preserve both sides:

set res(_res: Response | undefined) {
  if (this.#res && _res) {
    _res = createResponseInstance(_res.body, _res)
    for (const [k, v] of this.#res.headers.entries()) {
      if (k === 'content-type' || k === 'set-cookie') {
        continue
      }
      _res.headers.set(k, v)
    }
    // Preserve cookies from BOTH context and handler (issue #4992 Scenario B)
    const contextCookies = this.#res.headers.getSetCookie()
    if (contextCookies.length > 0) {
      const handlerCookies = _res.headers.getSetCookie()
      _res.headers.delete('set-cookie')
      for (const cookie of handlerCookies) {
        _res.headers.append('set-cookie', cookie)
      }
      for (const cookie of contextCookies) {
        _res.headers.append('set-cookie', cookie)
      }
    }
  }
  this.#res = _res
  this.finalized = true
}

Result:

Test Files  147 passed (147)
     Tests  4769 passed | 35 skipped (4804)

4,769 tests pass. 0 failures. 0 regressions.

The design conflict nobody talks about

This is the part most bug-fix blog posts skip.

Scenario A cannot be fixed without breaking existing tests. The #preparedHeaders field is designed for c.text(), c.json(), and other response constructors — NOT for merging into raw Response objects returned by handlers. Existing tests rely on this: a handler returning a raw Response should not have middleware's c.header() calls injected into it.

But issue #4992 Scenario A says that's exactly what should happen — middleware cookies should survive into the handler's raw Response. This is a design decision, not a code bug. The Hono maintainers need to decide: should c.header() before next() affect a handler's raw Response?

This is likely why the issue has been open for 2 months with no fix. It's not a missing line of code — it's a question about what the framework should do.

What the memory layer did

I captured the following to remem-mcp during this work:

  • Learning: The design conflict between #preparedHeaders and raw Response merging — captured with full context so a future session doesn't re-derive it.
  • Error: The 15-regression failure from fix attempt 1 — root cause was set-cookie handling inside the loop + merging #preparedHeaders when #res exists.
  • ADR: Architecture decision to scope the fix to Scenario B only, with Scenario A documented as needing maintainer input.

If I (or another agent) come back to this issue in a future session, recall("hono set-cookie merge #4992") would return the learning about the design conflict — saving the 30 minutes I spent discovering that Scenario A breaks existing tests.
